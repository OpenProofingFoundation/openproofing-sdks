# Pulse motion acquisition and custody reuse map

As of 2026-10-26. Source inspection only; no Pulse test, build, installation, device capture or data mutation was performed. This is a bounded extraction map for the Sensors SDK in `kenshiki-sdks`, not a new collection design. The accompanying [source manifest](acquisition-custody.sources.json) binds every implementation/test file used below to its read snapshot and end hash.

Pulse already supplies the acquisition adapters, pure canonical window routing, source provenance, typed aggregate contract, bounded staging custody, history cursor engine and erase ownership needed to start extraction. The work is primarily separation of these mechanisms from Pulse composition. Two existing behaviors need an explicit decision before adopting a stronger atomic-retention contract: durable aggregate windows do not retain every source sample, and journal projection eventually removes refused rows.

## Read boundary and authority

Read in full: Pulse root `AGENTS.md`, complete `CLAUDE.md`, `docs/evidence-graph.md`, `spec/sensor-atom-contract.md`; SDK root `AGENTS.md`, `CLAUDE.md`, and complete `governance/architecture/APP-ARCH-001.md`. The evidence graph's historical assertions were treated as routing/contract context, not proof of present acquisition behavior. All source claims below come from the current files listed in the manifest. Existing dirty work was preserved.

This audit begins at `SensorMonitor.start()` and the named `SensorLakeCoordinator` entry points. It does not claim to have audited every upstream scene/check-in scheduler, every other sensor, the full SQLite implementation, retention pruning internals, or complete product erasure. The SQL boundary was traced to the called `SQLiteLocalEvidenceLakeStore.append(contentsOf:)` operation; its transaction and key internals remain outside this bounded read.

## Active foreground path

1. [`SensorMonitor.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/SensorMonitor.swift), `start()`, checks the application's Motion & Fitness authorization branch and calls `startMotion()`. Its recorder is created and bound in `init()`; application-owned observable state and native manager lifetime live here.
2. [`SensorMonitor+Motion.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/SensorMonitor+Motion.swift), `startMotion()`, first asks `foregroundDeviceMotionRecorder.prepareForCapture()`. It requests `deviceMotionUpdateInterval = 1/12`, selects corrected/arbitrary Z-vertical reference frames when available, starts the recorder-history request, and delivers callbacks on the main operation queue. Its provider-generation/receipt gate precedes `handleDeviceMotion`.
3. `handleDeviceMotion` copies user acceleration, angular rate, gravity and attitude into mirrors. The durable aggregate recorder receives the original device-motion values before the display-publish gate. Separate display smoothing uses alpha 0.22/0.18; those smoothed mirrors are not fed to this aggregate recorder. Actual display gate is `SensorMonitor.displayPublishInterval = 1/4`, despite older comments in the extension saying approximately 6 Hz.
4. [`ForegroundDeviceMotionAggregation.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/ForegroundDeviceMotionAggregation.swift), `ForegroundDeviceMotionRecorder.ingest`, copies user acceleration, angular rate, gravity, actual attitude-frame identifier, magnetic calibration accuracy and sensor location into `DeviceMotionAggregateSample`. The pure `ForegroundDeviceMotionAggregation` owns source sessions and feeds `TumblingSensorWindow<DeviceMotionWindowReducer>`.
5. [`BoundedSensorWindow.swift`](../../../../pulse-ios/Sources/KenshikiDeviceSDK/BoundedSensorWindow.swift) routes half-open canonical 60-second monotonic bins. A sample on a boundary closes the old bin and is ingested into the next one. Invalid/repeated/out-of-order admission is counted or rejected; absent intermediate bins are not fabricated. A reference-frame or sensor-location change flushes `.sourceChanged` before opening a new source session. Stream errors flush `.interrupted`.
6. `ForegroundDeviceMotionRecorder.publish` submits completed windows to [`MotionAggregateLakeWriter.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/MotionAggregateLakeWriter.swift), `ForegroundDeviceMotionAggregateCustody`. There is one primary staging operation plus one final waiting aggregate. Occupying the final slot requests native acquisition pause; further submissions receive an explicit refusal. A failed stage retains the exact aggregate for retry; successful capacity recovery may restart acquisition.
7. `MotionAggregateLakeWriter.stage` admits a [`DeviceMotionEvidenceWindow`](../../../../pulse-ios/Sources/KenshikiDeviceSDK/DeviceMotionEvidenceWindow.swift), encodes through the single [`DeviceMotionEvidenceLakeAdapter`](../../../../pulse-ios/Sources/KenshikiDeviceSDK/DeviceMotionEvidenceLakeAdapter.swift), then calls `AppEvidenceLake.shared.journalSensorHistory([window])`.
8. [`AppEvidenceLake.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/AppEvidenceLake.swift) delegates staging to [`SensorHistoryJournalCoordinator.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/SensorHistoryJournalCoordinator.swift). [`LocalEvidenceBatchJournal.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/LocalEvidenceBatchJournal.swift) atomically writes the bounded JSON staging file. That successful file write is the acknowledgement boundary. SQLite projection is scheduled afterward, and can lag.
9. `SensorMonitor.stop()` flushes `.sourceStopped`, stops/releases native managers before awaiting durable stages, and returns the motion durability result. The awaited result establishes journal staging in this path, not independent SQL readback or physical acceptance.

The extension also writes legacy `motion_bucket` rows through its display-publish path with a 60-second throttle/minimum-state-change interval. Those sparse point-value payloads and the dense-derived `device_motion_window` aggregate are separate records. Their shared sensor ID does not make them interchangeable.

## Recorded acceleration history path

[`SensorLakeCoordinator.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/SensorLakeCoordinator.swift) supplies three concrete entry points. `recordPreEnvelope` and `recordHistoryBackfill` await acceleration-history collection alongside pedometer/activity. `recordDayPublicationBackfill` instead schedules acceleration history through `RecordedAccelerationHistoryImportOwner`, then awaits only pedometer/activity. The process-owned importer coalesces one active import and joins its cancellation on erase. Upstream callers of those entry points were not audited here.

[`RecordedAccelerationHistoryLakeWriter.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/RecordedAccelerationHistoryLakeWriter.swift) requests 12-hour recording and uses an injectable provider. Its provider queries off the main actor, in source chunks bounded to five minutes, with a three-minute publication safety delay and canonical minute cutoff. Cancellation is forwarded to the detached query and checked around source reads.

[`CoreMotionRecordedAccelerationSource.swift`](../../../../pulse-ios/Sources/KenshikiDeviceSDK/CoreMotionRecordedAccelerationSource.swift) enumerates one native list into owned `RecordedAccelerationWindowSample` values: sample date, sensor timestamp, acceleration vector and recording-batch identifier. Unavailable list and rejected-element count are explicit. The implementation does not mistake a batch identifier for an individual sample identity.

[`RecordedAccelerationWindow.swift`](../../../../pulse-ios/Sources/KenshikiDeviceSDK/RecordedAccelerationWindow.swift) deterministically sorts and deduplicates with bitwise identity handling, counts conflicting identities, routes wall-clock minute bins and finalizes only closed bins. It assumes nominal 0.02-second spacing for timing support, reports sensor-timestamp regressions separately, and retains no callback-latency fiction for retrospective input. The provider refuses conflicting/unroutable/rejected input instead of publishing a partial successful query from it.

[`SensorHistoryLakeEngine.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/SensorHistoryLakeEngine.swift) already owns reusable per-lane FIFO cursor/query/write serialization, permission/availability ladder, cancellation-aware callback bridge, bounded query timeout and explicit status rows. Current common lookback/catch-up bound is 12 hours; recorded acceleration selects a 30-second query timeout and 60.02-second cursor overlap. It reads the latest journal-aware successful history window, builds observed/status rows, then stages via `AppEvidenceLake.journalSensorHistory`. Its recorder lane serializes aggregate statistics, timing and recording-batch summaries/digest, not the retrieved source sample array. After successful projection and journal removal, those samples cannot be reconstructed from these aggregate payloads.

## Custody, replay and erase

- `LocalEvidenceBatchJournal` derives a batch ID from sorted row IDs and checks the same semantic rows on retry. Its staged reads bridge the gap before SQLite projection. A failed initial decode refuses subsequent staging through `loadFailed`; it does not overwrite the unreadable journal.
- `SensorHistoryJournalCoordinator.snapshot` merges staged/projected rows by ID with staged values winning, then applies deterministic bounds. `recent` filters before its cap. General `AppEvidenceLake.recentRead` remains SQLite-only; `journalAwareSensorHistoryRead`, snapshots and latest direct sensor reads use explicit overlay paths. Consumers must choose the correct consistency boundary.
- **Existing loss policy:** after three projection failures, the coordinator attempts each row separately, then removes the journal batch and logs refused rows. A store-wide failure can refuse every salvage append; there is no durable refusal/quarantine record in this coordinator before removal. The existing poison-batch test deliberately pins removal so later batches can progress. Extraction must explicitly reconcile that policy with any requirement to retain every acknowledged observation until durable acceptance or explicit owner-authorized disposal.
- [`SensorHistoryEraseCoordinator.swift`](../../../../pulse-ios/Samples/KenshikiDeviceDemo/Sources/SensorHistoryEraseCoordinator.swift) closes process admission, invalidates/joins registered owners, then reopens them. Its nested fence prevents an inner clear from reopening capture during an outer erase. `AppEvidenceLake.clearAll` raises the global erase barrier, closes capture, calls privacy clearing, independently clears journals/outboxes, exits the global barrier, then reopens capture. `ForegroundDeviceMotionAggregateCustody` drops retained retry work and joins an in-flight stage during invalidation.
- These are inspected cancellation/admission edges. Full privacy-service erasure internals, persistence registry completeness, SQL retention/pruning, key recovery and interruption-safe physical erasure were not independently audited in this tranche.

## Reuse boundary

| Existing mechanism | Recommended placement | What stays Pulse-owned |
| --- | --- | --- |
| Sensor session/clock/sample values, timing specification, canonical tumbling routing | Shared Sensors contract/window products | Pulse recording cadence/retention selection and lifecycle admission |
| Thin native device-motion and recorder-source copying | Optional Apple sensor acquisition adapter | Observable UI state, native permission presentation and multi-sensor monitor composition |
| Typed foreground evidence and validation | Versioned sensor observations; preserve historical Pulse v1 decoding in a compatibility adapter | Pulse sensor IDs, lane group, collection surface and lake payload vocabulary |
| Primary/final bounded staging, explicit pause/retry/settlement | Reuse mechanism behind an injected durable sink and host lifecycle | `SensorMonitor` callbacks, `AppEvidenceLake.shared`, health display and restart policy |
| History lane engine, cursor overlap, deterministic retrospective projection | Extract reusable parts with explicit source-specific time semantics | Day first-paint scheduling, check-in capture IDs, GPS-bound product composition and Pulse statuses |
| Journal overlay, staging identity, erase admission/join | Reuse against existing shared storage/erase foundations; reconcile loss policy first | Pulse singleton storage root, store registries and product erasure composition |

Do not copy Pulse's entire `AppEvidenceLake` or sensor monitor into foundation. The existing components expose practical seams already: reducer protocols, owned timestamped samples, provider ports, injectable stage closure, explicit completion reasons and erase-owner registration.
